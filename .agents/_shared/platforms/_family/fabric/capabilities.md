# Fabric Orchestration Sandbox Capabilities

All scripts live under the plugin's `scripts/platforms/_family/fabric/` directory, are Fabric-only, serve both Fabric kinds (`fabric_lakehouse` and `fabric_warehouse` — read the coordinates from the Intent's own `VD_EPHM_FABRIC_*` kind-named vars), and perform one capability each.

| Capability | Script | Result |
| --- | --- | --- |
| Upload dlt code | `upload-to-onelake.py --source <repo>/ingestion --workspace-id … --lakehouse-id … [--warehouse-id …] --domain-slug … --subdir ingestion` | `--source` must be the folder `--subdir` names, never the repository root — the script stores every path as `<subdir>/<rel>` relative to `--source`, and refuses a mismatch. Deletes `Files/<slug>/<subdir>/` and rewrites it from the tracked files, then writes `revision.txt` naming the commit — one copy, no history, because git is the version store. In the uploaded copy of `.dlt/config.toml` it rewrites the committed destination ids to the ones it was given (the repo file stays on the Domain ids), so the in-Fabric load lands in the same ephemeral resource the dbt job notebooks read: `[destination.filesystem]`'s `workspace_id`/`lakehouse_id` on a Lakehouse Intent, `[destination.fabric]`'s `workspace_id`/`warehouse_id` on a Warehouse Intent, where a committed staging `[destination.filesystem] bucket_url` also moves to the Intent's own Ephemeral Paired Lakehouse `Files/staging` (the run's `--workspace-id` and `--lakehouse-id`), so an Intent never stages into the production Paired Lakehouse. `--lakehouse-id` always names a **Lakehouse**: on a `fabric_warehouse` Intent that is the Ephemeral Paired Lakehouse (`VD_EPHM_FABRIC_WAREHOUSE_BRIDGE_LAKEHOUSE_ID`), never the Warehouse id — the Warehouse goes in `--warehouse-id` (`VD_EPHM_FABRIC_WAREHOUSE_ID`), and the script refuses a Warehouse config without it. |
| Upload dbt code | `upload-to-onelake.py --source <repo>/transformation --workspace-id … --lakehouse-id … --domain-slug … --subdir transformation [--prod-manifest /data/cache/prod-target/manifest.json]` | Delivers the project every dbt job notebook reads, like the dlt upload. The project goes up as committed; it refuses one with no committed `profiles.yml`. The Intent's own `~/fab_notebook_profile/profiles.yml` goes up beside it as `Files/<slug>/fab_notebook_profile/profiles.yml`, replacing an earlier one; without it the upload is refused, because the notebook would build the Intent's run into production. `--prod-manifest` adds a read-only copy of the production manifest at `transformation/prod-target/manifest.json`, refused unless it is a dbt manifest, before anything is written. |
| Import a notebook | `import-notebook.sh <name> orchestration/<name>.Notebook` | Imports the committed item as-is (updating one that already exists), attaches the ephemeral Lakehouse to the imported copy, and prints its id. |
| Prepare ephemeral copy | `prepare-ephemeral-import.py <item-dir> --workspace-id … --map <logicalId>=<objectId> … --out <tmpdir>` | Remaps portable references into a temporary copy; refuses a pipeline still invoking the retired dbt job. |
| Import a pipeline | `import-pipeline.sh <name> <item-dir>` | Imports one DataPipeline directory. |
| Run an item | `run-item.sh <name> <Notebook\|DataPipeline>` | Runs an item synchronously with `fab job run` and blocks until it ends (10–20 min for a dlt + dbt pipeline). Launch it with `start_async_bash` using `timeout_seconds: 1800`; use `wait_for_async_bash` with `wait_timeout_seconds: 300` when its outcome is needed. Never launch it twice for the same change. |
| Read dbt job evidence | `get-dbt-job-evidence.py --workspace-id … --lakehouse-id … --domain-slug … --pipeline-instance-id …` | Reads dbt's own `run_results.json` from `Files/<slug>/runs/<pipeline run id>/target/` — the folder the dbt job notebook points dbt at for that run — and prints the all-green line (when dbt generated it, `defer=on\|off`, node count); exits 1 when dbt never ran, the evidence predates the run, or any node is not green (`warn` included). |
| Export an item | `export-item.sh <name> <Notebook\|DataPipeline> <out-parent-dir>` | Exports native definition parts for evidence capture or authoring. |
