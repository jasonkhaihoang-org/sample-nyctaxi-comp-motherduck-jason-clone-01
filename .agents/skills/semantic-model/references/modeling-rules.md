# Modelling rules

The rules every Ossie document in the Domain's Ossie directory keeps, cited by number from `../SKILL.md`, `./refactoring.md`, `./reverse-engineering.md` and the `validating-semantic-model` skill. Payload field meanings live in `./vibedata-fields.md`; this file says how to use them.

## Stars are atomic; documents partition stars (S1)

A fact's star is the set of dimension keys the fact carries as columns: every foreign key on the fact is a relationship into that dimension, whether or not the fact's own SQL joins it. `physical_join` names the equi join a consumer would execute; the fact's own `FROM`/`JOIN` refs only decide which aggregate sources are honest. A fact star — its fact, those dims, its relationships, its metrics, its aggregate sources — lives wholly inside one document. It is never split across documents, and there is no shared-dimension document: Ossie resolves relationships within a document only, and the schema is closed, so a cross-document reference is unexpressible and a "shared dims" file would leave every star broken.

A table the population rule rules out is excluded, not given a document of its own, and so is a dimension no boundary fact can reach (an effective-dated reference table joined upstream): both take a `semantic_exclusions` reason in the repo map. A fact-to-fact key (an order line carrying `shipment_id`) stays a degenerate field on the referencing fact unless both facts live in one document; never import another star's fact as a dataset to express the path. Two stars in one document share one copy of a common dimension. Two stars in separate documents each carry their own copy, and the copies must agree on the dimension's identity — `source`, keys, and every field — while the role-specific parts stay local: a role alias (`ShipTo_Customer`) and a role logical source exist only in a document whose facts play that role. The validator compares same-named datasets, metrics, and physical tables across a directory and fails any that diverge in identity. A copied dimension declares `conformed_from: <owner document name>` in its VIBEDATA payload; the owner is the document whose star gives the dimension its meaning, and `validate` fails a copy that differs from it.

## Curated fields, not a mirror (S2)

`fields` are semantic attributes (keys, grouping/filtering dims, inputs to metric expressions) — a curated subset of the boundary dbt model, never a column dump. Degenerate non-semantic columns stay out. A field the Ossie dataset drops is a scope decision, recorded in the change, not an oversight. Money types are `Decimal`, other floating values `Float`, integrals `Integer`, and a vendor type outside the enum pairs `Opaque` with a `custom_extensions` note. Establish the type from the source column as the upstream or ingestion SQL produces it — never from the column name; where no SQL shows a cast, declare `Opaque` and record the unknown in the source `note`.

## Every field needs a supplying LTS (S3)

`logical_sources[].column_map` names the physical column behind each logical field or metric **per LTS**; an aggregate LTS maps only what its `content_grain` supports. Priority: detail-class `1` (one per role), aggregate `0`. Keep every detail at `1`: a consumer reads any non-zero value as detail supply, so inventing `2, 3, …` for aggregates makes an aggregate-only field look detail-supplied. Order aggregates with the source's own `join_cost` instead. Every declared field and metric needs a supplier; `suppliers` lists any that has none, and nothing supplies an item a mode invents locally. `content_grain` names the grain in the LTS table's own result columns — including a derived one such as `price_band` — falling back to the logical grain name only where no column expresses it; for a period-grain table name the period key (`order_month`), never just the entity key, which reads as a false grain. It is a human-readable declaration (list of strings), not a validated reference. Right-side (physical) columns are verified by you against the boundary dbt model SQL, never assumed identity — `validate` cannot see them, so a map onto a column that does not exist is green there; `ossie.py columns <model-dir> <catalog.json>` checks every mapped column, aggregate key column and field expression against dbt's catalog after a build (`dbt docs generate`).

A join narrows the population just as effectively as a filter — an inner join against a banding seed with half-open ranges, a non-null join, a `distinct` collapse. That makes the table population-narrowed, not an aggregate source (`./refactoring.md`); bind no metric whose population moves.

Metric names are compared across documents, so a name may not mean two populations: a metric answering a narrower population than the star's takes a scope-prefixed name (`billable_region_day_order_count`); a measure that also exists on another fact is named `<fact>_<measure>` (`shipment_order_count`); and a star metric name is never reused on a filtered table. A ratio is one metric whose expression divides two `SUM`s (`SUM(a) * 1.0 / NULLIF(SUM(b), 0)`), datatype `Decimal` — never two helper metrics a consumer might add. A ratio has no single backing column: in `column_map` it names its **numerator** column, and its `note` names the denominator column and the measure it comes from.

**Prove the population before binding a metric.** Read the aggregate's `FROM`/`JOIN` clauses, its `WHERE` and its `HAVING` — not only its aggregate columns — and reconcile the result against the ADRs that rule that population (a billable rule, a status verdict, an unresolved member). An inner join to a banding seed whose ranges exclude negatives, a spine that covers only some regions, a `HAVING` that drops thin groups: each makes the table's rows a subset of the star's, and the binding is wrong however exact the aggregation. A table that quietly contradicts an ADR is a business ruling to ask for, not a mapping to note. Do not write the population into the document. A rule goes to an ADR, the mechanics stay in the boundary dbt model SQL, and the reconciliation lives in a singular test — the source `note` points at that test. A prose population is a copy that goes stale the first time a filter moves.

Red-flag trap: mapping a filtered measure onto an unfiltered aggregate column, e.g. `billable_revenue` onto a monthly `total_revenue` — a monthly total is not billable-filtered revenue. No automated check can see this: treat every aggregate metric binding as guilty until the aggregate's SQL proves it innocent, and record that proof in the source's `note` (the `validating-semantic-model` skill reviews it).

## Content tells an engine when an aggregate may answer (S3b)

`content_grain` is for people; `content_levels` and `content_filter` are for the engine, and every aggregate source declares both. `content_levels` names, per dimension role, the level the source holds and the source's columns that carry that level's key (`key_columns`), so the source can be joined to the dimension at that level: a query grouping by anything finer cannot use it, and a role it omits is summed away. The physical join from the source to the table the role reaches must exist. `content_filter` states every row the source holds as a predicate over the dataset's declared fields — its `WHERE`, and also the rows its **inner joins** drop (a null dimension key, a null date key): an inner join is a filter. Report-window bounds are written as the literal dates the dbt vars that bound the boundary dbt model hold (in `dbt_project.yml`): dbt variables in a filter are not supported yet, and if the vars move without the Ossie document, `assert_semantic_content_holds` fails. Write the predicate from the SQL, regenerate the tests with `ossie.py generate-tests` (the content test compiles each aggregate binding and the detail under that predicate and compares them group by group at the source's content levels), and point the source `note` at `assert_semantic_content_holds`; every aggregate that binds a metric needs that pointer (`aggregate-binding-unheld`). A key the boundary dbt model inner-joins is filtered `IS NOT NULL` unless a `not_null` test guarantees it: a `relationships` test ignores nulls. A population no row predicate can state — a `HAVING` floor — is not an aggregate source: exclude the table (`semantic_exclusions` in the repo map). The detail source maps every metric too: when no aggregate's content covers a query, the detail is the answer.

A dimension with tables at several grains (a day calendar and a month calendar, a customer table and a segment table) keeps one dataset. The row-level table is its detail source; each coarser table is a `priority_group: 0` source whose `content_levels` names the dataset's own level, with no `via`, and its `key_columns`. It maps only what that level determines: its keys and attributes and those of coarser levels, never a finer field. An aggregate at that level joins the coarser table at the level's key.

## Metrics carry their rollup rule (S3c)

Every metric declares `aggregation`. A ratio or rate is a `derived_expression` over its numerator and denominator metrics and binds to no column, so an engine rebuilds it after aggregation at any grain; a precomputed rate column is refused on every source. A distinct count is `NON_ADDITIVE`. A level-based metric (`at_levels`), a time-series metric (`time_series`) and a dimension-based aggregation rule (`based_on_dimensions`: evaluate at the `across` level, then aggregate across that dimension with `AVG`, `MAX`, `LAST`, …) are consumption measures, in OBIEE terms all of them. Each wraps exactly one other metric and repeats its core `expression`. Add one only when a consumer needs the number, and never one whose meaning depends on a filter the Ossie dataset does not state. Before writing one, decide which ratio or average the question means (weighted ratio of totals, or equal-weight mean of per-group values) from the table in `./vibedata-fields.md`, and say which in the description. A semi-additive snapshot is `based_on_dimensions` with `rule: LAST` across a day level, not a plain `SUM`. Only members that have rows take part; densifying a calendar is a cube concern this semantic layer does not take on. The evaluation order there is normative: a logical-column formula is always applied last, to inputs already shifted or aggregated across a dimension.

A metric that reads a subset of its fact's rows declares that subset as `filter` (`orders.is_billable`), and its core expression reads the same columns: an engine matches the filter against an aggregate's `content_filter` to know whether the aggregate can answer. A metric grouped by a dimension its fact cannot reach fails by default (`unrelated_dimensions: error`). When a repeated total is genuinely wanted, as the denominator of a share across a dimension the fact does not have, declare a **separate** metric with `unrelated_dimensions: total`, and leave the base metric failing. Run `ossie.py dimensionality` to see what each metric reaches. A rolling window is `time_series` `ROLLING` over the calendar; a boundary dbt model column that rolls over rows is refused, because a missing day stretches it.

## Additivity decides which measure becomes a metric (S3a)

A measure is additive only across the dims it can be summed over. A semi-additive fact — machine down-days (sums across machines, not across overlapping ranges), a balance, a headcount snapshot, a stock level — never becomes a plain `SUM` metric, because every consumer will then sum it across the dim it forbids. State the additivity limit in the field description and in the fact dataset's `description`, then choose one: supply no metric, and record the refusal in the detail source's `note` with the shape a legal metric would need; define a metric that expands to the legal grain (a daily expansion, an end-of-period pick); or define a per-event mean as ratio-of-sums over the same event count, which never totals the measure and so does not cross the forbidden dimension. An aggregate source whose grain crosses the forbidden dimension cannot supply that measure at all. `validate` cannot tell a plain `SUM` of a semi-additive measure from a legal one, so this is a rule you keep, not a check that keeps you.

## Aliases are physical rows, not flags (S4)

A role-playing dimension is one dataset and N relationships: `customer` stays a single dataset, `orders_to_customer` and `orders_to_ship_to_customer` both target it with different `from_columns`, and each relationship's `physical_join` names its own `physical_tables` entry with `table_type: ALIAS` and `alias_of` pointing at the base table. Do not clone the dimension into `bill_to_customer`/`ship_to_customer` datasets — the endpoints that differ are the relationship's columns and the alias handle, not the dataset. A fan-trap is two or more declared paths into the same table with no distinguishing role; a bridge reached by one path needs no alias. Aggregate LTS tables point their joins at a dimension for reachability; no logical relationship backs them (aggregates aren't datasets), and that dangle is structural, not a smell. The core `from_columns`/`to_columns` are the join whenever the fact stores the as-of resolved surrogate; `scd_rollup: as_of` states the semantics. A `join_expression` is declared only for a join the core columns cannot express (a range or as-of predicate on a natural key), in Ossie `dataset.field` grammar over declared fields of the two datasets, and the compiler then joins on it. A `physical_join` naming no document-level join fails `validate`.

A bridge that fans a dimension member out to many rows (a store to its departments) lives in the star it serves. Its relationship joins the member, not a version (`to_level`), and carries the `weight` that allocates any measure crossing it from the one side. The weights of one member sum to 1, held by a singular test the bridge source's `note` names. Without a declared weight, no measure crosses that direction.

## Levels are declared from intent, keyed for joins (S5a)

A dimension declares its levels once (`levels[]`), and its hierarchies list them coarsest first; a level shared by two hierarchies (a day in Time and in Week) is one object. Each level carries `keys[]`, and every key identifies one member of its level **by declaration**. Exactly one key is primary: aggregate navigation, a join at the level and blending all use it. At most one is the display key. A field that describes a member without identifying it, such as a name several members share (`store_name` repeats across stores; `month_name` repeats every year), is an `attribute`, never a key. `row_level` says which level one row is: when rows are members, the dataset's `primary_key` is one of that level's keys (`date_key` and `calendar_date` both key a day); when rows are versions of members (Type 2), the `scd.natural_key` is the level's primary key and every hierarchy over it states `scd_rollup` (`as_of` or `current`).

Map a dbt model systematically, in this order: (1) the `primary_key` and every `unique` test or constraint in the boundary dbt model's properties YAML are candidate keys, and the column descriptions say which level each describes; (2) assign each candidate key to the level it identifies, choose the primary, and record readable columns that identify nothing as attributes; (3) write the hierarchies from the business's drill paths, not from what the data happens to satisfy; (4) for each aggregate, name the columns that carry each level's key. Never weaken a declaration because the data breaks it. Run `ossie.py generate-tests` to regenerate the two level tests. `assert_semantic_level_keys_hold` fails the build on what breaks a join at a level: a row-level primary key that repeats (on a Type 2 dimension, among its current versions) and a key that names several members. `assert_semantic_levels_hold` warns on the rest: a member with several values of a key, a member with several parents, and an aggregate key value that is no member. A reported row is a data finding for the boundary dbt model or the consuming tool (`row_number() = 1` and the like), recorded where it belongs, such as the source `note` or an ADR; a failing key is fixed in the boundary dbt model, never by weakening the level.

## SCD and hierarchies ride the dataset (S5)

Versioned dimensions declare `scd`, their business key in `unique_keys` (`[[natural_key, valid_from]]`), `levels[]`, `row_level` and `hierarchies[]` (S5a; a level of a versioned dimension is keyed by the natural key, so a member survives its versions) — all naming real fields (truly partitioned storage is `partitioned_by` on the physical table), all shaped per `./vibedata-fields.md`.

## The Ossie documents upgrade themselves (S6a)

The key set and the spec version move together, and the tool is the authority. When either changes, upgrade every document in the same change rather than leaving old ones behind:

1. Change the schema and the checker together; the parity test that compares the checker's key sets with `../scripts/vibedata-schema.json` is what stops the two drifting.
2. Rewrite every document mechanically — a script, never hand edits on payload lines — dropping or adding the affected key and stamping the new `vibedata_version` in every payload, so a document cannot carry two generations.
3. Run `validate`, `suppliers`, `notes` and `coverage`; a document left at the old shape fails `unknown-key` or the version check, which is the point.
4. Record the change in `./vibedata-fields.md` with what moved and why, so the next upgrade has a precedent.

A `note` cites what backs it and nothing else: `held by <test-name>` for a reconciliation and `ADR NNNN` for a rule. `notes` resolves both against the Domain's singular tests and decision-record directories, so a renamed test or a superseded ADR leaves a dangling pointer that fails rather than a sentence nobody dares touch.

## Frozen keys (S6)

The `VIBEDATA` key set per document component (Ossie's `model` component, dataset, relationship, metric) is closed and machine-readable in `../scripts/vibedata-schema.json`, with field-by-field meanings in `./vibedata-fields.md`. An unknown key fails validation (`unknown-key`). New keys arrive with their schema change, validator change, and tests, never by silent addition. `vibedata_version` rides every payload.

## Compile (S7a)

`ossie.py compile <model-file> <query-file>` turns a semantic query (`metrics`, `group_by` levels as `{via, level, key}`, an optional `filter` over the fact's fields, an optional forced `source`) into SQL and names the source it chose and why each other source was rejected. It reads an aggregate only when that is provably the detail's answer: every input bound with a SUM/MIN/MAX rollup, every grouped role held at or below the queried level, no rollup of a versioned dimension (that needs the fact's date), a query filter that contains every content-filter conjunct, and no `navigable: false` source unless named. Otherwise it reads the detail, through LEFT JOINs on many-to-one relationships. Rates are computed after their inputs. Level-based, time-series and dimension-rule metrics, multi-dataset metrics and `scd_rollup: current` raise an error instead of compiling. `generate-tests` and every exporter build on this compiler, so a rule changes in one place.

## Validate (S7)

Before commit, run the `validating-semantic-model` skill: it executes the structural gate (`validate`, `coverage`, `suppliers`, `notes`, `generate-tests --check`) and then reviews whether every mapping is honest. `validate` checks structure only — schema, names, references, payload keys, file naming — so a green run never means the content is right. The tool exits 1 on errors; a warning such as `table-unjoined` is factual (a table no join reaches), expected for aggregate handles.

After any mart change, update the Ossie documents in the same change.
