# Reverse-engineering and coverage

Use when onboarding a lakehouse into the semantic layer, when a new mart lands, or when a table has no honest mapping. Everyday edits do not need this file.

Scope is the boundary relations: facts, dims, aggregates and consumption tables. Relations in an `internal` layer are upstream of the semantic layer and never appear as handles, but a seed a boundary table joins is an input to that table, and a join against it that narrows the population is recorded with that table (see S3 in `./modeling-rules.md`). Build the inventory before partitioning documents: list every dbt model under the boundary layer paths, then read every boundary dbt model's FROM/JOIN refs, because a table's population — and so whether it is an aggregate source, a filtered metric or an exclusion (the routing table in `../SKILL.md`) — is only visible from its inputs. Every boundary table either has a handle in `physical_tables` (with its `dbt_model`) or carries its reason on itself: unmappable tables get a `note` on the physical-table entry, or a `semantic_exclusions` reason in the repo map when no star carries them (truncated, wrong star, bridge treatment); partially mapped sources get a `note` on the logical source naming each refused column and why. Reasons ride the entries so they cannot drift from them, or live in the repo map's `semantic_exclusions` when the relation has no entry. The rule binds both directions: reverse-engineering during onboarding enumerates and justifies gaps; forward-engineering a new dbt model registers it or justifies its absence in the same change.

When the Domain has an ontology, classify every boundary relation with `../../ontology/references/classification.md` while you read its SQL, and name the concepts a new mart populates: add their mapping entries through `ontology` in the same change. The `coverage` gate forces the Ossie document; nothing but this step forces the ontology to notice. A mart that carries no concept of its own gets no mapping, and its document's description says why.

When a table cannot be honestly mapped (SQL unreadable, grain ambiguous, truncation or filtering defeats every honest mapping, bridge treatment unclear), stop and grill the user. One question at a time, one item per question, waiting for the answer before asking the next: what the table is, why it is blocked, the options with a recommendation, and what unblocks each option. Answer from the code anything the code can answer, so no question asks for what you could have read. A batch of questions in one message is not a grilling — the user cannot answer four interleaved decisions at once, and the first answer usually changes the rest. Ask first; write the entry plus its `note` only once ruled — never pre-create entries for undecided items. Skipping silently and assuming are both failures — the former hides the gap that rule exists to close, the latter writes a lie the validator cannot catch. Record the user's ruling as a `note` on the entry in the same change.

For each aggregate or consumption mart you register as a logical source, write its content from the SQL in the same pass, not afterwards. `content_levels` comes from its `GROUP BY`: one entry per dimension role it groups by, naming the level that column keys (a `date_trunc('month', ...)` is the month level; a store natural key is the store level), with `via` set to the relationship the mart's join actually follows and `key_columns` set to the grouping columns that carry the level's key (`key` names a non-primary key when the mart groups by that one, such as a payment method's name). A grouping column that keys no declared level is recorded in the `note`, not invented as a level. `content_filter` comes from its `WHERE` **plus every inner join**: each inner join to a dimension drops the fact rows whose key is null, so it adds `<key> IS NOT NULL`. Window bounds are the literal dates the dbt vars hold (dbt variables in a filter are not supported yet); the generated content test fails if the two drift. Then regenerate the tests with `ossie.py generate-tests`, whose `assert_semantic_content_holds` compiles each bound metric for the source and for the detail under the filter and compares them group by group at the source's content levels, and point the `note` at it. A `HAVING` or other group-level cut makes the table an exclusion (`semantic_exclusions` in the repo map), not an aggregate source.

Declare levels from the dbt metadata and the business's intent, never from what the data happens to satisfy: follow the four mapping steps in S5a of `./modeling-rules.md` (candidate keys from `primary_key`, `unique` tests and constraints; assign each to its level and choose the primary; non-identifying readable columns become attributes; hierarchies from the drill paths). Then run `ossie.py generate-tests` and `dbt test --select assert_semantic_level_keys_hold assert_semantic_levels_hold`; fix the key in the dbt model it fails on, and record what the second reports as data findings, leaving the declaration as written. Give every metric an `aggregation`; write a rate as a `derived_expression` over the metrics for its numerator and denominator, and refuse the rate columns aggregates carry. A dbt model column that averages, maximises or picks the last of per-group values (an average daily count, a peak day, a closing balance, a mean of per-employee rates) is a dimension-based aggregation: declare it as `based_on_dimensions` across the inner level with that rule, and refuse the column, because it cannot roll up.

A dbt model that filters its rows (billable only) supplies a metric whose `filter` states that filter, not a renamed copy of the unfiltered metric. A bridge dbt model (one row per member and child, with a share column) joins its star as a weighted bridge, with a test that the shares sum to 1. A dimension dbt model at a coarser grain than its dimension (a month calendar, a segment table) is a coarser source of that dimension, not a new dataset. A dbt model column that rolls a window over rows (`rows between 6 preceding`) is refused in favour of a `ROLLING` metric.

Ask versus note-only: when the SQL leaves exactly one honest disposition (wrong star by its own header, truncation that defeats every mapping), record the `note` directly under the coverage rule. When two or more dispositions are plausible, or the analysis itself is uncertain (contradictory grain evidence, undefined treatment), ask under this rule.
